# Findhouse MVP 技術架構

- 更新日期：2026-07-11
- 目標：本機優先開發，未來可部署至 Cloudflare

## 1. 架構原則

- 採單體式全端應用，不拆微服務。
- 選用 Cloudflare Workers 相容的框架與套件。
- 本機使用 Wrangler 模擬 D1 與 R2，正式環境只更換綁定與機密設定。
- 資料庫不依賴 PostgreSQL 專屬功能，以維持 D1 相容性。
- 圖片、寄信與驗證均透過獨立模組封裝，避免供應商細節散落在頁面程式。

## 2. 目標架構

```text
瀏覽器
  │
  ▼
Next.js／React on Cloudflare Workers
  ├── 公開房源頁
  ├── 帳號與 Email 驗證
  ├── 約看流程
  ├── 管理頁
  └── API 與權限檢查
        ├── D1：結構化資料
        ├── R2：房源圖片
        └── Email Provider：驗證及通知信
```

## 3. 執行環境

### 3.1 本機

- 應用程式在本機啟動。
- D1 使用本機持久化資料。
- R2 使用本機模擬 bucket。
- Email 預設為測試模式，輸出可檢查的郵件內容或使用供應商測試環境。
- 本機機密放在不提交版本控制的環境檔。

### 3.2 正式環境

- 應用部署至 Cloudflare Workers。
- 資料存放於正式 D1。
- 圖片存放於私人 R2 bucket，由應用控制上傳與讀取。
- 驗證與通知信由交易型 Email 服務寄送。
- 正式機密使用 Cloudflare secrets，不寫入程式或資料庫。

## 4. 模組邊界

```text

├── 公開欄位過濾
├── 費用與電費規則驗證
├── 禁止內容檢查
└── 重要條件版本與通知

├── 上傳驗證
├── R2 object 操作
└── 圖片排序與封面

├── 私人文件上傳與版本
├── 短效授權預覽

├── 政策文件版本
├── 個別告知與同意紀錄
├── 資料保存與刪除工作
├── 檢舉、申訴與管理處置
└── 管理稽核

viewing
├── 房源提供者可約時段管理
├── 時段保留與併發控制
├── 確認期限與排程式自動取消
├── 申請與狀態轉換
├── 預約編號產生與核對
├── 碰面資訊與異動歷程
├── 權限檢查

├── 站內通知
```

逾期處理由 Cloudflare 排程事件觸發，查找已超過確認期限且仍為待確認的預約。處理必須具備冪等性，重複執行不應再次改變狀態、釋放時段或寄送通知。本機測試需能以明確指令觸發相同處理邏輯，不依賴實際等待。

## 5. R2 圖片策略

- bucket 預設不允許匿名寫入。
- object key 由系統產生，例如 `properties/{propertyId}/{uuid}.{ext}`。
- 上傳前檢查 MIME type、副檔名、檔案大小及圖片數量。
- 不使用使用者原始檔名作為公開路徑。
- 資料庫保存 object key、MIME type、尺寸、大小、排序與替代文字。
- 正式圖片讀取可經 Worker 或受控公開網域；實作前依快取與隱私需求定案。
- 第一版只使用少量固定顯示尺寸，避免產生不受控的圖片轉換組合。

## 6. R2 私人文件策略

- 所有權文件與公開房源照片使用不同 bucket；若環境限制必須共用，至少使用不同 binding、路徑與存取政策。
- 私人文件 bucket 不開放公開讀取，也不使用 `r2.dev` 公開網址。
- 上傳時檢查允許格式、MIME type、檔案大小及頁數，object key 不包含姓名、地址或原始檔名。
- 預覽請求必須檢查提交者或審核者權限，並使用短效存取方式。
- 重新補件寫入新 object，不覆蓋舊版本。
- D1 保存文件 metadata、版本、審核及存取紀錄，不保存文件二進位內容。
- 標章狀態只能由審核結果產生，R2 上傳成功本身不能取得標章。
- R2 或 D1 部分失敗時不得產生錯誤的審核通過狀態，並需保留可重試紀錄。

## 7. Email 策略

- Email 供應商透過單一 adapter 串接。
- 驗證 token 只能儲存雜湊，並具有用途、到期時間與單次使用限制。
- 寄信與主要資料交易分開記錄；寄信失敗不得回滾已成功的約看狀態。
- 正式環境設定 SPF、DKIM、寄件網域與退信處理。
- 所有 Email 連結以伺服器端驗證，不能只依賴前端參數。

## 8. 安全與營運底線

- 所有寫入操作進行伺服器端驗證與授權。
- 登入、驗證信重寄、密碼重設、約看申請、圖片及私人文件上傳需限制頻率。
- 密碼使用成熟函式庫的安全雜湊，不自行設計加密。
- 管理員角色不得由一般會員自行修改。
- 資料所有權在伺服器端檢查：會員只能管理自己的房源及收到的預約，管理員可管理全站資料。
- 預約編號不得作為授權憑證，也不得提供公開編號查詢端點。
- 房源欄位驗證必須在伺服器端執行，包括押金上限、條件式電費欄位與禁止內容；不能只依賴前端表單。
- 住宅租賃規則需保存規則版本，未來法規更新時可辨識每筆房源使用的驗證基準。
- 服務條款、隱私權政策、會員規則及敏感文件告知分別版本化；不能只在 `users` 保存最新布林值。
- 重大版本可設定 `requires_reconsent`，會員未重新同意時只限制受影響功能，不得阻止查看政策、匯出／處理帳號或行使個資權利。
- 資料保存與刪除需依資料類型執行，並記錄成功、失敗與可重試狀態。
- 個資不寫入日誌；錯誤追蹤需遮蔽 Email、電話與 token。
- 文件預覽、下載、審核與標章撤銷必須留下不可由一般使用者修改的稽核紀錄。
- 審核者不得審核自己提交的文件。
- D1 migration、R2 object 與應用版本需有可追蹤的部署流程。

## 9. 未來擴充界線

資料模型保留 `property_id`，但第一版不建置多房源介面。未來增加多房源時，新增列表、搜尋、刊登與房東權限，不應改寫既有約看與圖片關聯。

第一版不建立通用工作流引擎、微服務、訊息佇列或複雜 CMS；只有在真實用量與失敗情境證明必要時才引入。
